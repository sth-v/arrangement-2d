### Interface change requests

- ops.hpp owner (documentation, no code change): `polyline::point()` and `polyline::subcurve()` return **Kind::Segment** boxes (as ops.hpp's own comments specify), but every `KindOps` method rejects a foreign kind via `require_point`/`require_kind`. So `ops(Polyline).point_approx(polyline::point(c, 0))` throws KindMismatch and callers must `convert_point()` first. This bit my test immediately. The Python layer already does the right thing (`_as_point(it, _K_POLYLINE)`), but a one-line warning in ops.hpp next to those two declarations ("the returned box has Kind::Segment; convert_point() it before feeding it back to polyline ops") would save the next reader. Alternative (larger): let `require_kind` accept a foreign kind whose boxed C++ type is identical, which would make segment/linear/polyline points interchangeable.
- ops.hpp owner (documentation): `KindOps::approximate(c, tolerance, clip, out)` does not say whether `out` is cleared or appended. `KindOpsBase::approximate_length` and the Cython layer both pass a fresh vector, so it does not matter today; I chose to `out.clear()` first. Please state the contract (I suggest 'clears out'), since `make_x_monotone`/`intersect` in the same interface *append*.
- ops.hpp owner (documentation): `convert_curve` does not say which `GeomType` the produced boxes carry. I emit `GeomType::XCurve` for every real conversion (everything convertible into a polyline is a straight segment or an x-monotone piece, so the stronger box type is always correct and is accepted everywhere a Curve box is), and return the input unchanged for the polyline->polyline identity. If other kinds pick a different rule the Python `to_kind()` results will be inconsistent; worth pinning down across the kind TUs.


### Open issues

- `polyline::make_x_monotone()` relies on CGAL's own `CGAL_precondition` for the x-monotonicity of the point range (Arr_polyline_traits_2.h:573-575), as ops.hpp specifies ('Precondition error otherwise') and as my task note directed. I do pre-check the cheap parts myself (>= 2 points, consecutive points distinct -> Error(InvalidArgument) naming the index), but if the library is ever built with `-DNDEBUG` *without* `-DCGAL_DEBUG`, a non-monotone chain would silently build an invalid X_monotone_curve_2 instead of throwing. DESIGN.md pins `-DNDEBUG -DCGAL_DEBUG` and I verified the precondition still fires under exactly those flags. If that flag pairing is ever relaxed, this function needs its own monotonicity loop (about 10 lines, mirroring CGAL's compare_x/compare_xy rule).
- `convert_curve`'s generic (registry-based) route can only *prove* straightness for source kinds that provide `Construct_x_monotone_curve_2(p, q)` — segment, linear, polyline, conic, sphere. A **straight** circle-segment curve (`_X_monotone_circle_segment_2::is_linear()` with rational endpoints) IS exactly representable as a polyline, but the circle-segment traits has no such functor (traits_circle_segment.md gotcha 3), so it currently gets Error(NotRepresentable) telling the user to convert through the segment kind. Supporting it directly would mean including circle_segment_types.hpp here and unpacking its Sqrt_extension coordinates; I judged the extra coupling not worth it, and deliberately refused rather than guessing (a chord-midpoint test would be unsound for wiggly Bezier pieces).
- `approximate()` genuinely ignores its `tolerance` (a polyline's exact geometry IS the returned chain, so there is nothing to subdivide) and ignores `clip` (polylines are always bounded). The tolerance is still validated (> 0, NaN rejected) so Python sees identical behaviour across kinds; the documented 1e-12 clamp is computed and then unused. If a future caller wants a *coarser* polyline (vertex decimation within `tolerance`) that would be a new function, not this one.
- `KindOps::approximate_coordinate` deliberately keeps the base implementation, i.e. the raw `Arr_polyline_traits_2::Approximate_2(p, i)`, which uses `CGAL::to_double(Epeck::FT)` and is up to one ulp off; `point_approx` (what `Point.x` / `.approx` use) is correctly rounded. ops.hpp and the Python `Traits.approximate_point` docstring both describe the former as raw-functor access, so this is intended, but the two differ visibly (0.33333333333333337 vs 0.33333333333333331) and the test prints both. If the project would rather have one answer everywhere, override `approximate_coordinate` in every kind TU to delegate to `point_approx`.
- An *empty* `Polycurve_2` (0 subcurves) cannot be produced by any function in this TU, but a hand-built box could hold one; `curve_bbox`, `xcurve_source`, `xcurve_target` and `to_curve` reject it with Error(InvalidArgument), while `approximate` returns an empty vector, `number_of_points` returns 0 and `curve_is_bounded` returns true. Documented behaviour, not exercised by the test (there is no supported way to construct such a box).

### Interface change requests

- impl/kind_ops_base_impl.hpp owner (cross-kind consistency, medium priority): the generic `KindOpsBase::approximate_coordinate` calls `traits().approximate_2_object()(point, i)` whenever the traits has the functor. For every Epeck-based traits that functor is `CGAL::to_double(Lazy_exact_nt)` (Arr_segment_traits_2.h:911), which is NOT correctly rounded — measured in this session: for x = 1/3 it returns 0.33333333333333337 while the correct double is 0.33333333333333331. That contradicts CGAL_TRAPS_CHECKLIST.md ("Never use CGAL::to_double(Epeck::FT) or Approximate_2 for user-visible doubles") and makes approximate_coordinate() disagree with point_approx() on the same coordinate. I overrode the method in SegmentOps (kind_segment.cpp, `approximate_coordinate`); segment, linear, polyline, circle_segment and sphere are all affected. Proposed fix in the generic layer: drop the `if constexpr (has_approximate_coord)` branch entirely and always delegate to the kind's own `point_approx()` (which is exactly what the current `else` branch already does for Bezier). That is a 4-line deletion in kind_ops_base_impl.hpp and would let the five kind TUs drop their overrides.
- ops.hpp owner (optional, low priority): KindOps has no way to ask a curve of another kind whether it is a straight segment, nor for its algebraic degree. Because a kind TU may not call another kind's free functions (link contract), `SegmentOps::convert_curve` has to certify "this conic/Bezier arc IS its chord" geometrically, by testing k_chord_samples = 6 interior chord points with the source traits' exact Compare_y_at_x_2. That is exact and complete for conic (degree 2) but only certifies polynomial Bezier curves of degree <= 7. A `virtual int curve_degree(const Geom&) const` (0 = unknown) or a `virtual bool xcurve_is_linear(const Geom&) const` on KindOps would make the conversion exact for any degree and cheaper. Purely additive.
- arrangement.hpp owner (documentation only): `ArrBase::locate(p, strategy)` with an unknown strategy id (e.g. 42) throws Error(Unsupported) via ArrImpl::require_pl, not Error(InvalidArgument) as the header's neighbouring wording suggests. My test asserts the actual behaviour; worth one sentence in the header so the Python layer maps it consistently.


### Open issues

- conic/Bezier -> segment conversion: the exactness certificate is `both endpoints rational` + `the arc passes through 6 interior rational points of the chord` (exact Compare_y_at_x_2 of the SOURCE traits). By Bezout an algebraic curve of degree d that is not contained in a line meets it in at most d points, so 8 collinear incidences certify degree <= 7. Conic arcs (degree 2) are therefore fully certified; a polynomial Bezier of degree >= 8 that is not the chord but happens to meet it at all 8 tested points would be converted WRONGLY. CGAL's Bezier traits does not produce such curves in this project's use, and the constant `k_chord_samples` is one line to raise, but the limitation is real and is documented at the call site. See also the interface change request about a `curve_degree()` query.
- That conic/Bezier branch is exercised only against a purpose-built stub KindOps registered under Kind::Conic in the test (a straight chord vs. a parabola through the same endpoints), because linking kind_conic.o/kind_bezier.o into this per-kind test is explicitly out of scope. Once those TUs exist, a cross-kind integration test should convert a real conic 'special segment' arc and a real degree-1 Bezier into segments.
- KindPolicy<SegmentTypes>::supports_triangulation is true (segment is the only kind with straight edges and a Kernel), but CGAL_TRAPS_CHECKLIST.md records that Arr_triangulation_point_location silently returns the WRONG face for faces with holes. My test only queries faces it handles correctly and says so in a comment. Whoever owns the Python layer should either document the restriction or flip the flag; it is not a kind_segment.cpp decision.
- CGAL::remove_curve does not merge the degree-2 vertices an input curve leaves behind: after removing the crossing curve from the square the arrangement is V=6 E=6 F=2, not V=4 E=4. Asserted and commented in the test; it is CGAL's documented with-history behaviour, but Python users will notice.
- approximate(curve, tolerance, clip, out) validates the tolerance (>0, NaN rejected, clamped up to 1e-12) but then ignores both it and the clip box: a segment's exact polyline approximation is its two endpoints. This matches CGAL's own segment traits (its Approximate_2 spells the parameter `double /* error */`) and keeps the cross-kind contract uniform.
- `_Segment_cached_2::line()` memoises the supporting line through a mutable member on first use, so `segment::supporting_line()` mutates the shared curve representation and is not safe to call on the SAME curve object from two threads at once. Documented at the call site; harmless under the GIL.
- `arr2d::segment::make/make_xy` return GeomType::XCurve boxes (a segment is always x-monotone), which is what `_geometry.pxi` needs for `Curve.is_x_monotone`. convert_curve normalises its output to XCurve boxes for the same reason. If any consumer expects GeomType::Curve from these constructors, it will need `ops.to_curve()`.

### Open issues

- MEMORY, BY DESIGN: Bezier `Curve_2` objects are never freed. `Curve_2::id()` is the rep address and both traits caches are keyed by it and are never invalidated (traits_bezier.md gotcha 7), so kind_bezier.cpp keeps every Curve_2 it ever sees in a process-lifetime `std::deque<Curve_2>`. A session that builds N distinct Bezier curves therefore retains N reps (control-point deque + two lazily built integer polynomials) plus the monotonically growing Bezier_cache / Intersection_map (there is no `_Bezier_cache::clear()`). This must be documented in the Python user docs. There is no safe alternative in CGAL 6.1; the test proves the id of a dropped curve is not recycled.
- PERFORMANCE: `point_approx()` (and hence ArrImpl::vertex_coordinates(), ArrImpl::bbox() and approximate()'s endpoint snapping) calls `make_exact(cache)` on a non-rational point. That is required for accuracy — an inexact _Bezier_point_2 approximates to its bbox CENTRE, measured 0.075 off, i.e. 75x the requested error (rendering_and_approximation.md gotcha 12) — but it means bulk-exporting the vertices of a large Bezier arrangement runs exact CORE algebra once per vertex. The result is memoised in the point rep (Handle_for is shared, so every copy of the box benefits) and in our cache, so it is paid once. If profiling ever shows this hurts, the fallback (bbox centre, always safe) is one `if` away, at the price of visibly wrong coordinates.
- `point_is_rational()` is deliberately conservative: it returns `Point_2::is_rational()` only. `make_exact()` never fills the rational coordinates of an algebraic point (traits_bezier.md §4.3) and CORE has no safe rationality test for an Expr (a false EQUAL against a rational convergent is documented in exact_coordinates_contract.md gotcha 1), so a coordinate that happens to be rational is reported as algebraic. Python sees an Algebraic with a certified interval instead of a Fraction.
- DEVIATION FROM THE TASK WORDING (deliberate): `curve_bbox` of an x-monotone piece uses the double control polygon RESTRICTED to the piece's exact parameter range (two de Casteljau splits), not the bbox of the approximate() polyline. By the convex-hull property that is a guaranteed SUPERSET of the arc, whereas a polyline's bbox can cut a bulge off; it also needs no tolerance argument. The exact endpoint approximations are unioned in. The test verifies containment of 21 sampled curve points per piece.
- TRAITS LIMITATION (not ours, will surface in Python): CGAL's Bezier `Intersect_2` returns NO overlap for two x-monotone subcurves of the SAME Curve_2 with the same xid (`if (_xid == cv._xid) return false;`, Bezier_x_monotone_2.h:2123). `curve.intersect(sub_curve_of_itself)` therefore yields only shared endpoints. Already noted by the stage-1 kind_ops_base author; nothing in this TU can fix it.
- TRAITS LIMITATION: `Multiplicity` is 0 or 1 only and does not mean multiplicity (0 = unknown/rational/endpoint, 1 = simple/approximated). Passed through verbatim; the test only asserts `multiplicity <= 1`.
- CGAL BEHAVIOUR worth documenting for users: `remove_curve()` does NOT merge the degree-2 vertices left where the removed curve crossed a surviving one — `Arrangement_on_surface_with_history_2::_remove_curve` calls the plain `Base_arr_2::remove_edge(he)`, which drops an endpoint only when it becomes isolated. Measured: removing B2 from the 2-curve arrangement gives V=7 E=6 (not V=4 E=3); a follow-up `remove_vertex()` on each redundant vertex merges 3 of them and gets to V=4 E=3. The regions.py helpers may want to do that automatically.
- `convert_curve` from the conic / circle-segment / sphere kinds is Error(Unsupported) with a reason: a circular or conic arc is a RATIONAL Bezier curve, and CGAL's Bezier traits only handles polynomial ones (DESIGN.md). A tolerance-bounded approximation (the DESIGN.md `BezierCurve.approximate_rational`) is a Python-level feature and is not implemented here.
- `bezier::point_parameter` and `point_originators` return the exact algebraic parameter only when the originator carries one. If a point acquired an extra originator through `compare_xy`'s originator merging AFTER it was made exact, that originator has only a bound interval; `point_originators` then reports the bound midpoint and `point_parameter` raises Error(Unsupported) with an explicit message. Not observed in the test, but the code path exists.

- `linear::direction()` is NOT normalised. For a segment it is `target - source` (as ops.hpp mandates); for a ray/line it is the supporting line's `to_vector() == (b, -a)`, sign-corrected to the stored traversal direction. CGAL's coefficients are themselves unnormalised in the general case, so e.g. the segment (0,0)-(4,3) gives (4,3) while the line y=x gives (1,1) and the horizontal ray gives (1,0). If Python wants a canonical direction it should reduce it there.
- `curve_repr` prints a line as `Line(a=..., b=..., c=...)` using CGAL's stored coefficients. `line_from_pointsC2` normalises horizontal/vertical lines to ±1 forms but leaves general lines at the raw `(py-qy, qx-px)` scale, so two geometrically identical lines built from different point pairs can have different reprs. `curve_equal` is unaffected (it compares supports up to opposite).
- `convert_point` from a kind whose TU is not linked (bezier / conic / sphere in a per-kind unit test) falls through to `arr2d::ops(kind)` and therefore reports `Unsupported("kind not available")` rather than `NotRepresentable`. In the shipped library all seven kinds are linked, so this only shows in isolated tests. Segment / Polyline / CircleSegment are handled natively and need no registry entry.
- `remove_curve` of one of three concurrent lines leaves the two degree-2 vertices the removed line had created (measured V=3, E=6, F=4, still valid): CGAL does not merge the collinear edges around them. Worth knowing before writing Python-level assertions about counts.
- The C++ test prints two `CGAL error:` blocks to stderr while exercising the two traps. That is CGAL's default handler on Apple clang printing before it throws (number_types_and_errors.md gotcha 5); both exceptions are caught and asserted on. The Python module installs a silent handler at import, so this is test-only noise.
- `approximate()` deliberately ignores `clip` for BOUNDED curves (segments), per the ops.hpp wording that clip exists "to clip unbounded curves". This is also what makes `KindOpsBase::approximate_length()` (which passes `clip == nullptr`) work. A renderer that wants segments clipped to the viewport must do it itself.
- `ArrImpl::he_directed_curve` returns an unbounded curve AS STORED (it checks `curve_is_bounded` before calling `construct_opposite`), so `face_polygon` of an unbounded linear face returns rays whose stored direction may run against the halfedge. Callers must consult `he_direction()` for those — this is the documented contract in arrangement.hpp; my test asserts that all 6 unbounded faces now produce a polygon instead of the Unsupported the stage-1 stub ops produced.
- `convert_curve` from Kind::Polyline emits one linear segment per SUBCURVE, so a polyline becomes several curves; from Kind::CircleSegment only a straight piece with rational endpoints converts. Conic/Bezier/Sphere are refused with Error(Unsupported) naming the kind, as required — there is no straight-line image for them.

### Open issues

- CGAL's batched point location and vertical decomposition are unsafe on the sphere for boundary points/vertices (see the two interface_change_requests). Until arr_impl.hpp guards them, `arr2d::sphere::point_location(p) != NO_BOUNDARY` is the pre-filter the Python layer must apply to `batched_locate` queries, and `decompose` must be gated on "all vertices interior".
- `CGAL::zone` / `CGAL::do_intersect` of a curve LYING ON the identification meridian abort with the Compare_xy_2 precondition, and they miss the incidence when the query curve's MAXIMAL end is exactly the north pole (traits_geodesic_sphere.md gotchas G6 and §10.10 items 3-4). - Incremental `insert_curve` of a curve that lies ON the identification meridian aborts once the arrangement already crosses that meridian (gotcha G1). The recommended path is the aggregate `insert_curves` (used by the test for exactly such a case: the full (0,1,0) great circle). `ArrBase` exposes both; the Python layer should prefer `insert_curves` for the sphere.
- `point_approx` is not bit-exact scale invariant: (1,1,1) normalises to 0.57735026918962584 and (7,7,7) to 0.57735026918962573 — 1 ulp apart, both inside the certified `point_interval` and both within 1 ulp of 1/sqrt(3). The exact components are identical directions; only the double normalisation differs. Asserted in the test with a 1e-15 tolerance.
- `curve_bbox` is derived from the polyline approximation at a hard-coded tolerance of 1e-6, so it is an approximate box: for a full equator it reports y in [-0.999999001, 0.999999001] instead of [-1, 1] (the sample nearest the extremum is half a step away). CGAL offers nothing exact — `Arr_x_monotone_geodesic_arc_on_sphere_3::bbox()` is `#if 0`-ed out. If an exact box is ever needed, it can be computed from the arc's normal and endpoints in closed form; say the word and I will add it.
- A very small tolerance is clamped to 1e-12 rather than rejected: that still means ~2.2e6 chords (≈53 MB of doubles) for a full great circle. Documented in code; if a hard cap on the point count is wanted, ops.hpp should say so.
- `sphere::is_degenerate()` and the degenerate branches of `approximate()` / `to_curve()` are unreachable through the public API (no constructor produces a degenerate arc), so they are implemented and commented but not covered by the test.
- `SphereTypes::traits()` uses a plain function-local `static const Traits` as the task specified. That is safe here (Epeck, no CORE::Expr), but it does mean the traits object is destroyed during static teardown while the leaked `SphereOps` singleton still holds a pointer to it. Design points worth calling out:
* Coordinates are `CGAL::Sqrt_extension<Epeck::FT, Epeck::FT, Tag_true, Tag_true>` (traits gotcha 1). Every exact/approx/interval conversion goes through `impl/number_conv.hpp`; rationality is decided with `sqrt_ext_is_rational()` (a perfect-square radicand keeps `is_extended() == true` — exact_coordinates_contract gotcha 3), and `make_point_sqrt` normalises a provably rational value back to the un-extended form.
* `approximate()` uses the traits' `Approximate_2(xcv, error, back_inserter, l2r)` with `l2r = xcv.is_directed_right()` so the polyline always runs source→target; the tolerance is validated/clamped to `(1e-12, inf)` first (`error <= 0` SIGSEGVs — rendering gotcha 7) and a `std::back_insert_iterator` is mandatory (gotcha 6). A general `Curve_2` is subdivided and the pieces concatenated with the duplicated junction points dropped (gotcha 4); a full circle therefore comes out as a **closed ring** starting and ending at the leftmost point and running in the circle's own orientation; a zero-radius circle yields its centre once.
* `curve_bbox()` computes a **tight** box instead of using `_X_monotone_circle_segment_2::bbox()`, which always widens y to the full-circle extremum and uses undirected `to_double`. The interior y-extremum is detected with `is_in_x_range(centre)` + `point_position(centre)` and evaluated as `cy ± sqrt(r²)` through certified `interval_of(SqrtExt)`.
* `approximate_coordinate()` is overridden to route through `point_approx()` — the traits' `Approximate_2` point overload is `CGAL::to_double(Epeck::FT)`, which is not correctly rounded (CGAL_TRAPS_CHECKLIST "Numbers / coordinates").
* Every CGAL construction precondition is checked here and reported as `arr2d::Error` (endpoint-on-circle, endpoint-on-line, distinct endpoints, orientation ±1, r² sign, p1≠p3). The on-circle/on-line tests are written exactly as CGAL writes them, because *adding* two `CoordNT`s with different radicands trips `Sqrt_extension::check_roots`, while `CGAL::compare` handles different radicands exactly (ACDE_TAG = Tag_true).
* `convert_point` / `convert_curve` unbox foreign geometry through the raw CGAL types from the other kinds' header-only `*_types.hpp` (Segment/Linear/Polyline all share `Epeck::Point_2`), so they work with **no link dependency** on those TUs; only bezier/conic/sphere points fall back to `arr2d::ops(kind)` and report `Unsupported("that kind is not linked")` when absent.

`src/arr2d/tests/test_kind_circle_segment.cpp` (1200 lines) is a self-contained 450/453-assertion test with hand-derived expected numbers in comments and both compile+link command lines in its header.

### Conventions

Conventions established / followed by this kind TU, for the other kind implementers and the Cython layer:

STRUCTURE. A kind TU includes only `arr2d/kinds/<kind>_types.hpp`, `arr2d/impl/kind_ops_base.hpp`, `arr2d/impl/number_conv.hpp`, `arr2d/impl/arr_impl.hpp`, `arr2d/{bso,ops,registry}.hpp` — never the `*_impl.hpp` of kind_ops_base directly. File-local helpers live in an anonymous namespace inside `namespace arr2d` so both the Ops class and the `arr2d::<kind>` free functions can use them. Errors are raised through one `[[noreturn]] bad(ErrorCode, msg)` helper that prefixes every message with "circle_segment: ".

FOREIGN GEOMETRY WITHOUT LINK DEPENDENCIES. `convert_point` / `convert_curve` unbox other kinds by including their header-only `*_types.hpp` and testing `Geom::holds<T>()`, never by calling that kind's free functions (which would create an undefined symbol when only this TU is linked). Segment / Linear / Polyline all use Epeck, so a single `holds<Epeck::Point_2>()` test covers all three points. Kinds that genuinely need their own ops (bezier/conic/sphere) go through `kind_available(k)` + `arr2d::ops(k)` and report `Error(Unsupported, "... that kind is not linked into this build")`.

NUMBERS. Never `CGAL::to_double` and never the traits' `Approximate_2` point overload for user-visible doubles: `point_approx`, `point_interval` and (overridden) `approximate_coordinate` all go through `to_double_correctly_rounded` / `interval_of` from number_conv.hpp. Rationality of a `Sqrt_extension` coordinate is decided with `sqrt_ext_is_rational()` (never `is_extended()`), and `point_exact` uses `box_sqrt_extension`, which normalises a rational value to a Rational box. `make_point_sqrt` normalises the other way (a provably rational a+b*sqrt(c) becomes an un-extended CoordNT).

SQRT ARITHMETIC. Two `CoordNT`s with different radicands may be COMPARED (`CGAL::compare`, exact because ACDE_TAG == Tag_true) but must never be ADDED or SUBTRACTED (`Sqrt_extension::check_roots` is a precondition on `+=`/`-=`/`*=`). All precondition tests are therefore written in CGAL's own "compare(lhs, rhs)" shape rather than "sign(lhs - rhs)".

PRECONDITIONS. Everything CGAL only asserts is checked here first and reported as `arr2d::Error`: endpoint-on-circle / endpoint-on-line (exact, in CGAL's own formulation), distinct endpoints, orientation in {+1,-1}, squared radius sign, p1 != p3 for the three-point ctor, (a,b) != (0,0) for a line. Behaviour CGAL defines but which surprises users is documented instead of blocked (three collinear points silently build a segment; a zero-radius circle is a legal degenerate curve that make_x_monotone turns into a single isolated point).

APPROXIMATION. Validate and clamp the tolerance BEFORE any CGAL call (`> 0`, floor 1e-12), always pass `std::back_inserter`, and pass `l2r = xcv.is_directed_right()` so the output runs source->target as ops.hpp promises. Concatenating the x-monotone pieces of a general curve drops the duplicated junction points; a full circle is emitted as a CLOSED ring (first point == last point) starting at the leftmost point and running in the circle's own orientation.

BBOX. Prefer an exact, tight box over CGAL's `bbox()` where the latter is loose: for an x-monotone circular arc the only interior y-extremum is at x == cx, detected with `is_in_x_range(centre)` + `point_position(centre)` and evaluated as `cy ± sqrt(r²)` through `interval_of(SqrtExt)`; all coordinates come from certified intervals (lo for minima, hi for maxima) so the box is always a valid enclosure.

REPR. `Circle(center=(cx, cy), squared_radius=r2, orientation=ccw|cw)`, `CircularArc(center=..., squared_radius=..., orientation=..., source=(...), target=(...))`, `Segment((x, y), (x, y))`. Rationals print as `n` when integral and `n/d` otherwise; sqrt coordinates print as `a + b*sqrt(c)` (or `a - |b|*sqrt(c)` when b < 0).

SINGLETONS. `Types::traits()` is one function-local static, never copied, constructed with `use_intersection_caching == false`. The KindOps object is heap-allocated and deliberately leaked inside the registrar (`static XOps* ops = new XOps();`) because KindOpsBase owns a leaked traits adaptor and must never be destroyed.

TESTS. A kind test links registry.o numbers.o overlay.o + its own kind TU and defines the polygon-set factory as a stub under `#ifdef ARR2D_TEST_STUB_BSO`; both command lines (with the stub, and without it plus the real bso_<kind>.o) are spelled out verbatim in the file header and both are verified. Foreign-kind geometry is fabricated in the test with `make_geom(Kind::X, GeomType::…, <raw CGAL object>)` using that kind's header-only types. The test must exit 0 (proving no abort during static destruction) and prints "<n> checks, <k> failures". Remember that `KindOps::make_x_monotone` and `KindOps::intersect` APPEND — clear the output vector between calls.

### Open issues

- `to_curve(xcurve)` rebuilds the general `Curve_2` with the (Circle_2, source, target) constructor, so the result always has `m_has_radius == false` — there is no CGAL constructor taking circle + radius + endpoints, and the flag is protected. Consequence: a round trip xcurve -> to_curve -> make_x_monotone recomputes the vertical tangency points as sqrt extensions even when the radius is rational. Values are unaffected (I verified the half-circle round trip still yields exactly 1 x-monotone piece); only the coordinate representation gets more expensive. Documented at the call site.
- `convert_curve` accepts Segment, bounded Linear objects, Polyline subcurves and its own kind; conic and Bezier curves report NotRepresentable. A *segment-type* conic arc or a degree-1 Bezier with rational endpoints IS exactly representable, but reading those raw types would pull the CORE-based conic/Bezier headers (and the CORE MemoryPool exposure) into this TU. If that conversion is wanted, the clean route is `arr2d::ops(Kind::Conic)` + the `conic::`/`bezier::` free functions once those TUs are guaranteed to be linked; today they are not (a kind test links its own TU only).
- CGAL's `_X_monotone_circle_segment_2::can_merge_with` is "same supporting curve AND share an endpoint", so the two halves of a circle that share a tangency point report `are_mergeable() == true` even though their union is the whole circle and is not x-monotone. I did not rely on it in the test (I use an arc + a segment for the negative case), but the Python layer should be aware that `can_merge` is not a promise that `merge` yields an x-monotone curve for co-circular arcs.
- Intersection caching is deliberately OFF (`Arr_circle_segment_traits_2(false)`): the cache is a `mutable` std::map with no clear() that grows for the life of the process, and with caching off every x-monotone curve carries index 0, which disables a few same-supporting-curve fast paths in has_same_supporting_curve / _lines_compare_to_right / _circs_compare_to_right. If profiling ever shows this matters, flipping the flag is a one-word change but reintroduces unbounded memory growth.
- `CircleSegmentTypes::traits()` is a plain function-local static (no CORE::Expr is involved in this kind, so the MemoryPool trap does not apply). I checked that the arrangement's destructor path (Arrangement_on_surface_2::~/clear_all, the topology traits' init_dcel, ~_Circle_segment_2) never calls into the traits, so even an ArrImpl destroyed after static destruction would be safe. The KindOps singleton and KindOpsBase's traits-adaptor copy are both leaked on purpose, as the stage-1 conventions require.
- For the BSO agent (not my file): `CGAL::convert_polygon(CGAL::Polygon_2<K>, traits)` does not work with this traits (it needs construct_curve_2_object, which does not exist) — traits_circle_segment.md gotcha 3 gives the by-hand recipe. Also `Gps_traits_2::Equal_2(Polygon_with_holes_2, Polygon_with_holes_2)` contains a real comma-operator bug (gotcha 9).
- The polyline branch of `convert_curve` uses `internal::Polycurve_2::subcurves_begin()`, i.e. a CGAL-internal type reached through PolylineTypes::Curve_2. It compiles and is tested, but it is coupled to `CGAL::internal::` and would need revisiting if the polyline kind ever changes its Curve_2 typedef.

Every GPS traits instance and every `Gps_traits_adaptor` is heap-allocated and deliberately leaked (General_polygon_set_2 stores the traits BY POINTER, gotcha 4; and CORE-backed statics abort at exit with `! blocks.empty()`).

Key design decisions (all commented in the code with the gotcha they address):
* orientation() uses `Gps_traits_adaptor<GpsTraits>::Orientation_2` for EVERY kind including segment, NOT `CGAL::Polygon_2::orientation()`: the latter goes through `CGAL::orientation_2()`, whose `CGAL_precondition(is_simple_2(...))` is ACTIVE under `-DNDEBUG -DCGAL_DEBUG` and would make a "must not throw" helper throw for a self-intersecting boundary. Using the adaptor also makes `orientation(ring) > 0` exactly the condition `insert()` validates against (it is what CGAL's own `has_valid_orientation_polygon` uses). The test cross-checks agreement with `CGAL::Polygon_2::orientation()` for simple polygons.
* Structural guards before Orientation_2 (closed chain of >= 2 curves with a local leftmost vertex), because CGAL's functor dereferences its "leftmost" iterator unconditionally and would read `end`.
* is_closed_chain / orientation / is_valid_polygon go through the GPS traits + adaptor, NOT `arr2d::ops(kind)`, so a `bso_<kind>.o` links and works without the corresponding `kind_<kind>.o`. Only `to_arrangement()` needs the kind registry — proven: a segment-only build (bso_segment.o + registry/numbers/overlay only) runs 111 checks green.
* insert()/insert_polygons()/*_polygon() validate with `CGAL::is_valid_polygon` (bounded, no holes) or `is_valid_polygon_with_holes` FIRST and throw `Error(InvalidArgument)` with a message naming the actual defect ("...clockwise orientation; CGAL requires counterclockwise outer boundaries...", "...not a closed chain...", "hole 0 has counterclockwise orientation...").
* The `*_polygon` Boolean variants build a temporary set with OUR traits and use the set-vs-set form, because CGAL's `_join(const Polygon_&)` etc. build a DEFAULT-constructed `Aos_2 second_arr;` (its own traits => a second Bezier/conic cache).
* clone() does NOT use CGAL's copy ctor (which does `new Traits_2(*m_traits)`); it constructs with our traits and assigns the arrangement, which keeps the traits pointer and copies the `contained` flags via `Gps_face_base::assign`.
* Self-operations are special-cased (`join(self)`/`intersection(self)` no-op, `difference(self)`/`symmetric_difference(self)` clear) — CGAL would delete `m_arr` while reading it (gotcha 3).
* Only the binary `do_intersect(const Self&)` is used (gotcha 2: the range form is inverted). Only `Equal_2`'s POINT overload is used (gotcha 12).
* `to_arrangement()`: inserts all boundary curves, then marks as contained the face to the LEFT of every correctly-directed boundary curve (a curve with `Compare_endpoints_xy_2 == SMALLER` is traversed by the `ARR_LEFT_TO_RIGHT` halfedge). Doing this for EVERY curve, not just the first of each polygon, also handles a region split into several faces by a hole touching the outer boundary (verified: the symmetric-difference case yields 2 contained faces). Unbounded polygons additionally add `arr->unbounded_face()` (covers the whole-plane case, where there are no curves at all). Representative halfedges are collected during insertion and resolved to faces only AFTERWARDS — resolving eagerly is wrong because an unclosed chain still has the unbounded face on both sides (found and fixed by the no-history probe).
* `Policy::insert_with_history`: true for segment/circle_segment/conic (KindOps::to_curve round-trips exactly), false for Bezier, whose `to_curve()` returns the whole SUPPORTING curve — inserting it would add geometry off the polygon boundary; Bezier therefore uses `insert_non_intersecting_curve()` per curve (exact, no curve history).

### Interface change requests

- polygon_set.hpp owner (doc only, no code change): `insert()` is documented as "throws Precondition error otherwise". The implementation instead validates with CGAL::is_valid_polygon / is_valid_polygon_with_holes BEFORE calling CGAL and throws arr2d::Error(ErrorCode::InvalidArgument) with a message naming the defect (orientation / not-closed / hole orientation / not simple). Rationale: the CGAL precondition is compiled away under -DNDEBUG (the map's gotcha 5: the set is then built anyway and is_valid() returns false), and Error(InvalidArgument) carries a far better message. Please update the comment on PolygonSetBase::insert / insert_polygons.
- polygon_set.hpp owner (doc only): `is_closed_chain` follows CGAL's is_closed_polygon semantics — an EMPTY chain returns true (vacuously closed) and a SINGLE-curve chain returns false ("a polygon cannot have just a single edge", Gps_polygon_validation.h:195). Worth stating in the header so the Python layer does not assume `is_closed_chain([]) == false`.
- polygon_set.hpp owner (doc only): PolygonGeom's `unbounded` flag. An EMPTY `outer` always means unbounded, because that is CGAL's own representation (General_polygon_with_holes_2::is_unbounded() == outer_boundary().is_empty()). The impl therefore accepts `unbounded == false` with an empty outer and >= 1 hole and treats it as unbounded, and REJECTS `unbounded == true` with a non-empty outer. Suggest documenting that in the PolygonGeom comment.
- polygon_set.hpp owner (cosmetic, optional): `PolygonSetBase::is_valid()` is const, but CGAL's Gps_on_surface_base_2::is_valid() is NOT const (it is a read-only O(E) sweep that CGAL simply forgot to mark const). The impl uses a const_cast. Making the virtual non-const would remove the cast; keeping it const is also fine and is what the Cython layer already assumes.
- registry.hpp / bso.hpp owners: nothing needed — the four kind TUs already wire `&arr2d::make_polygon_set_<kind>` into KindEntry::make_polygon_set (verified by grep and by the registry-path checks in the test).


### Open issues

- CGAL's `do_intersect(const Self&)` and `oriented_side(const Self&)` internally build a DEFAULT-constructed `Aos_2 res_arr;` as the overlay target — an arrangement with its OWN default-constructed traits. For the conic and Bezier kinds that means a second, independent conic intersection cache / Bezier_cache is created for the duration of the call. It is inside CGAL and cannot be avoided without reimplementing the overlay-functor path. All conic/Bezier do_intersect and oriented_side_of_set checks passed, but this is the one place where the process-wide cache is NOT shared. If it ever misbehaves, the fix is to implement do_intersect as clone+intersection+!is_empty() (which allocates its result as `new Aos_2(m_traits)`); oriented_side_of_set cannot be replaced that way because it distinguishes boundary-touch from overlap.
- `to_arrangement()`'s with-history branch pairs `chs[i]` with `curves[i]`, relying on ArrBase::insert_curves() returning one curve handle per input curve IN INPUT ORDER (documented in arr_impl.hpp / STAGE1_NOTES). A `std::min(chs.size(), curves.size())` guard keeps it from reading out of range if that ever changes, but a reordering would silently pick wrong faces. Verified correct for segment, circle_segment and conic by the contained-face counts.
- The Bezier kind's `to_arrangement()` produces an arrangement with NO curve history (number_of_curves() == 0), because a _Bezier_x_monotone_2 sub-arc has no equivalent general Curve_2 (KindOps::to_curve returns the whole supporting curve). Everything else about the arrangement is exact. If history is ever required for Bezier, ops.hpp would need a `to_curve_exact(xcurve) -> optional<Curve_2>` or the with-history classes would need to accept x-monotone input.
- `insert()` / `insert_polygons()` do NOT check CGAL's second precondition — that the inserted polygons are completely disjoint from the current content and from each other (`_insert` only ever uses non-intersecting insertion). Checking it costs a full Boolean operation, so it is left as a documented CGAL precondition; callers with possibly overlapping input must use join_polygon(). Violating it triggers a CGAL assertion (or silent corruption under -DNDEBUG).
- `Gps_circle_segment_traits_2<K>` cannot be constructed from an existing `Arr_circle_segment_traits_2<K>` (its only constructor takes `bool use_cache`), so the circle-segment GPS traits is an INDEPENDENT instance from CircleSegmentTypes::traits(), built with use_cache=false (CGAL's default). Harmless — that traits' only state is the flag plus a mutable memo table — but it is the one kind where the GPS traits is not derived from the kind's traits.
- CGAL prints `CGAL warning: check violation! ... The polygon has a wrong orientation. / is not simple.` to stderr from is_valid_polygon* whenever a polygon is rejected. That is the documented, accepted behaviour (the task allows it), but the Python layer may want to install CGAL::set_warning_behaviour / a silent error handler at import so a rejected polygon does not spam stderr before the exception is raised.
- Measured CGAL behaviour worth documenting for users: the symmetric difference of [0,2]^2 and [1,3]^2 is ONE polygon-with-holes (an octagon with a 4-curve hole), not two polygons — the two L-shaped pieces touch at the two corners (1,2) and (2,1) and CGAL emits them as a single relatively-simple p-w-h. `to_arrangement()` on that set correctly reports TWO contained faces. The task brief expected 2 polygons; the test asserts the measured value and explains why.
- `Gps_traits_2<T>{Types::traits()}` relies on Gps_traits_2 being a C++17 aggregate (no declared constructor, no data member, one public base). Verified with `std::is_aggregate` plus a compiling probe against CGAL 6.1. If a future CGAL adds a constructor or a data member to Gps_traits_2, the two CORE-backed policies need a different way to copy-construct the base (e.g. `struct X : ConicTypes::Traits { X() : ConicTypes::Traits(ConicTypes::traits()) {} };` used as the Gps_traits_2 template argument). A static_assert would be a cheap guard if the ABI contract doc wants one.
- bso_conic.o and bso_bezier.o reference ConicTypes::traits() / BezierTypes::traits() and therefore need kind_conic.o / kind_bezier.o at link time (that is deliberate: it is what makes the caches shared). bso_segment.o and bso_circle_segment.o need no kind TU at all — verified by two standalone test builds.

### Interface change requests

- ops.hpp owner (optional, low priority): namespace arr2d::conic has no `make_arc_three_points(p, q, r)` even though CGAL's Construct_curve_2 has the three-rational-points circular-arc overload (traits_conic.md 2.4) and namespace arr2d::circle_segment does expose `make_arc_three_points`. Suggested addition: `Geom make_arc_three_points(const Geom& p, const Geom& q, const Geom& r);` (p source, q interior, r target; rational points). I did NOT add it because ops.hpp lists the exact signature set I own. Everything it would do can be had today through make_from_five_points or make_circle_arc.
- ops.hpp owner (optional): `conic::make_full(r,s,t,u,v,w)` takes no orientation while `make_circle` and `make_ellipse` do; the full-conic overload of Construct_curve_2 derives the orientation from the coefficient signs, so a caller who wants the other traversal must negate all six coefficients himself. Adding an `int orientation` parameter (0 = 'as given by the coefficients') would make the three full-conic constructors symmetric. Two-line change in this TU once the header changes.
- ops.hpp owner (optional): the hyperbolic-safety predicate is only reachable through the constructors (as Error(Unsupported)). A query such as `bool conic::supporting_conic_is_supported(const Rational& r, ..., const Rational& w)` would let the Python layer pre-check a curve (and let a caller decide between rotating the scene and switching kinds) without building and catching. It is implemented in this TU as `arr2d::conic::detail::hyperbolic_axis_is_sound` with external linkage, so promoting it is a one-line declaration.
- ops.hpp owner (already raised by the kind_ops_base implementer, re-confirmed here): `IntersectionResult::multiplicity` is `unsigned` while `Arr_conic_traits_2::Multiplicity` is `std::size_t`; KindOpsBase narrows with a static_cast. Harmless today (observed multiplicities are 0-3).
- No blocking change requests: impl/arr_impl.hpp, impl/kind_ops_base*.hpp and impl/number_conv.hpp all compiled and worked for this kind without modification. KindPolicy<ConicTypes> was already specialised in arr_impl.hpp and its matrix (naive/simple/walk/landmarks/trapezoid supported, triangulation not, ray shooting via simple/walk/trapezoid, free CGAL::is_valid usable) is confirmed correct at RUNTIME by the test.


### Open issues

- DOCUMENTED LIMITATION (as the task anticipated): `point_is_rational` is ALWAYS false and `point_exact_rational` ALWAYS throws NotRepresentable for conic points, because CORE offers no sound rationality test for `Expr` (exact_coordinates_contract.md gotcha 1: an Expr built by this traits can compare EQUAL to a rational convergent that is provably different, breaking transitivity) and `Conic_point_2` cannot carry a 'built from rationals' flag. CONSEQUENCE the task did not spell out: the three constructors that genuinely need rational input -- `make_from_five_points`, `make_from_rational_bezier`, and the Rat_segment_2 fast path of `make_segment` -- therefore REFUSE conic points with Error(NotRepresentable) and a message telling the caller to pass a rational point of another kind. The Python layer is unaffected in practice because DESIGN.md's `a2.Point(x, y)` defaults to kind SEGMENT. `make_segment` still accepts conic points: it falls back to the exact 'special segment' overload, which is geometrically identical but reports all-zero coefficients. A sound fix would need either a CORE exactness flag or a leaked rational registry keyed on the Expr rep address (rejected: it would leak memory per Python Point).
- DEVIATION from the task note 'curve_bbox from the approximation': curve_bbox uses `traits.construct_bbox_2_object()` (which traits_conic.md gotcha 13 names as the correct replacement for the UB `Conic_arc_2::bbox()`, and which uses the exact vertical AND horizontal tangency points), then UNIONS it with a polyline approximation at tolerance max(1e-9, 1e-3 * extent) and with the exactly rounded endpoints, and finally widens by 4 ulps on each side. Rationale: Construct_bbox_2 converts through CGAL::to_double without outward rounding, so the raw box is not certified; an approximation alone can only ever be inside the true box and would miss a tangency extremum unless the tolerance were driven to 0 (which for a unit-radius arc at 1e-12 would emit ~2^20 points). `Conic_arc_2::bbox()` is never called.
- `to_curve()` on an x-monotone arc whose supporting conic is hyperbolic re-enters `build_hyperbolic_arc_data()`. Such an arc can only exist if `conic::set_allow_hyperbolic(true)` was used, in which case a CGAL::Assertion_exception may escape from to_curve (and from `ArrImpl::insert_curve` when an XCurve box is inserted). Documented at the call site; not gated, because gating there would contradict the user's explicit opt-in.
- `conic::set_allow_hyperbolic` is a process-wide `std::atomic<bool>`, not per-thread and not per-arrangement. With it on, CGAL can build arcs that answer point containment and Intersect_2 incorrectly while `arr.is_valid()` still returns true (traits_conic.md 13.6) -- the Python docs should say so loudly.
- Converting a Bezier X_monotone_curve_2 of degree > 1 raises Error(Unsupported): the x-monotone piece is a sub-arc whose endpoints are algebraic _Bezier_point_2 values that need the Bezier kind's own cache. Degree-1 Bezier x-monotone curves and general Bezier Curve_2 of degree 1 and 2 convert exactly. Converting a Bezier POINT works only when `is_rational()`.
- Linear rays and lines cannot be converted (Error(Unsupported)): a conic arc is always bounded. Sphere geometry gives KindMismatch. Both are deliberate.
- The traits' intersection cache (`m_inter_map`) is never cleared and the adaptor held by KindOpsBase is a second, independent copy of it (already noted by the kind_ops_base implementer). For a long-lived Python process with many distinct conic pairs this grows without bound; there is no API to drop it short of rebuilding the traits, which we cannot do because it is leaked by design.
- `Make_x_monotone_2` burns one process-global conic id per call (traits_conic.md gotcha 11). `approximate()` and `curve_bbox()` on a general Curve_2 each make one such call, so repeated rendering of the same curve consumes ids (a std::size_t counter -- no practical risk, but worth knowing).
- Not covered by this task and untested here: the Boolean-set-operation path (bso_conic.cpp, written in parallel -- the test only proves it links and that the registrar's factory pointer resolves), overlay between two conic arrangements, and the Arrangement_2-level modification API (split_edge/merge_edge/modify_edge/insert_from_*_vertex), which is generic in ArrImpl and was covered by the stage-1 segment tests.
