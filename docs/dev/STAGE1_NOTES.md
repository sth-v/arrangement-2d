### Summary

Implemented the two files assigned: `src/arr2d/include/arr2d/impl/number_conv.hpp` (conversion/boxing/approximation/comparison helpers for the kind TUs and the Cython bridge) and `src/arr2d/src/numbers.cpp` (every function declared in `numbers.hpp`, plus the non-inline part of number_conv.hpp).

Key implementation decisions:
* `to_double_correctly_rounded(Rational)` is a hand-written exact round-half-to-even conversion (exact binary exponent from `msb(n)-msb(d)` with a one-step correction, integer quotient + remainder, half-even tie break, `ldexp`), with shortcuts to +-inf at E>=1024 and +-0 at E<-1076. It handles subnormals exactly. `rational_to_double` delegates to it. `CGAL::to_double(Epeck::FT)` is never used (map gotcha #2 — verified in the test: CGAL gives 0x3FD5555555555556 for 1/3, ours gives the correct 0x3FD5555555555555).
* `interval_of(Rational)` is exact floor/ceil in doubles (correctly-rounded double + one `nextafter` step decided by an exact rational comparison) — tight, certified, and monotone. All other intervals are built on it.
* `interval_of(SqrtExt)` / `to_double_correctly_rounded(SqrtExt)` use exact rational sqrt bounds from an integer `isqrt` of `p*q*2^(2k)` (relative error 2^-k). `to_double` refines k = 64,128,...,4096 until the two endpoints round to the same double (guaranteed to terminate for an irrational value; a perfect-square radicand is detected first and handled exactly).
* `interval_of(Algebraic, bits)` = `Expr::approx(bits,bits)` + `BigFloat` `makeFloorExact`/`makeCeilExact` -> exact dyadic `BigRat` bounds -> floor/ceil doubles (the recipe from number_types_and_errors.md §4.3). Never uses `BigRatValue()` on the Expr itself. `to_double_correctly_rounded(Algebraic)` refines 64..4096 bits until the enclosure collapses to one double, falling back to `Expr::doubleValue()`.
* SqrtExt comparison is exact through `CGAL::Sqrt_extension<Rational,Rational,Tag_true,Tag_false>::compare`. I verified in the header that with `ACDE_TAG = Tag_true` the default is `in_same_extension == false`, i.e. CGAL takes the exact different-roots branch — so the CORE::Expr fallback the task allowed for is NOT needed (still verified against the Expr images in the test: `1+sqrt(2) == 1+2*sqrt(1/2)`, `sqrt(2) < sqrt(3)`).
* `box_sqrt_ext` / `box_sqrt_extension` normalise: a rational-valued a+b*sqrt(c) (b==0, c==0, or c a perfect square) is boxed as a Rational. `number_is_rational` uses the same predicate (a superset of the header's "b==0 or c==0"), and `number_to_sqrt_ext` is deliberately lenient about a Rational box (otherwise normalisation would make it unusable).
* All string parsing is hand-written (map gotcha #3: `istream >> Exact_rational` mis-parses "0.125" as 0 without failbit, `Exact_rational("0.125")` throws, and `CGAL::IO::iformat` lets Boost throw `std::runtime_error("Division by zero.")` out of "1/0"). Grammar: `[ws][sign]{digit}['.'{digit}][(e|E)[sign]digits][ws]`, plus an `n/d` split; absurd decimal exponents (|net| > 1e6) are rejected as InvalidArgument instead of allocating 10^1e9.
* `number_repr` for Algebraic is `%.17g` followed by a trailing `~` marker (documented in the file).

### Open issues

- `number_interval(Algebraic, bits)` can never return an interval narrower than 1 ulp of a double, because the result type is `std::pair<double,double>`. `bits` genuinely controls the internal CORE refinement (measured: the exact rational enclosure is 1.5e-123 wide at bits=200 vs. 2.2e-16 for the returned doubles), so the returned pair is monotone/nested but usually saturates at 1 ulp immediately. If Python's `Algebraic.refine(bits)` is meant to expose progressively tighter bounds, the C++ interface would need to return exact rationals (or strings) rather than doubles — say the word and I can add `void number_interval_exact(const Geom&, int bits, Rational& lo, Rational& hi)`; the machinery (`expr_enclosure`) is already there, just file-local.
- CORE global state is process-wide and NOT thread-safe (number_types_and_errors.md §9): `Expr::approx`, `Expr::cmp`, `Expr::sign`, `BigFloatValue` all mutate shared/lazily-allocated node state, and `defRelPrec`/`defAbsPrec` are plain non-atomic globals. numbers.cpp does no locking, so every Algebraic path (`to_core_expr`, `interval_of(Expr,...)`, `to_double_correctly_rounded(Expr)`, `number_compare` involving an Algebraic, `number_repr` of an Algebraic) must be serialised by the caller / kept on one thread. Whoever owns the Cython bridge should decide where that lock lives.
- The `arr2d::compare(...)` overloads shadow `CGAL::compare` for exactly matching argument types inside `namespace arr2d` (see the WARNING block at the top of number_conv.hpp). I verified with a consumer TU that this is NOT ambiguous and that the arr2d (non-template) overload wins for Rational/Epeck::FT/SqrtExt/CORE::Expr pairs, and that `CGAL::compare(...)` spelled explicitly still works. Anyone wanting a `CGAL::Comparison_result` must qualify.
- `to_double_correctly_rounded(Algebraic)` falls back to `CORE::Expr::doubleValue()` (not guaranteed correctly rounded) in the single case where the refinement loop fails to converge after 4096 bits — that happens only for an Expr whose exact value sits precisely on a double rounding tie. Documented in the source.
- Boost expression templates: `to_double_correctly_rounded((lo+hi)/2)` was ambiguous (the expression template is not a `Rational`, and `CORE::Expr` is implicitly constructible from `BigRat`). Fixed by materialising a `Rational` temporary. Other TUs calling these overloads with a Boost arithmetic *expression* rather than a named `Rational` will hit the same ambiguity — bind to a `Rational` first.
- No CGAL error handler is installed by this file. Per number_types_and_errors.md gotcha #5, on Apple clang CGAL's default handler prints the 'CGAL error:' block to std::cerr before throwing; whoever owns module init must call `CGAL::set_error_handler(no-op)`.

### Interface change requests

### Interface change requests

- arrangement.hpp declares `const char* obs_event_name(ObsEvent)` but nothing defines it (registry.cpp does not). Whoever owns registry.cpp / a future arrangement.cpp should add the snake_case name table; I deliberately did not define it in overlay.cpp to avoid a duplicate symbol.
- common.hpp defines `operator==` for VH/HH/FH/CH but no `operator!=`; C++ callers currently have to write `!(a == b)`. Suggest adding the four `operator!=` overloads (purely additive).
- ArrBase::insert_from_left_vertex / insert_from_right_vertex have no `FH containing_face` parameter. CGAL requires one when the vertex has degree 0 and carries no isolated-vertex record; with the current signature that case is a CGAL precondition failure. If the Python API should support it, the interface needs an optional face argument (not required for the isolated-vertex case, which works).


### Open issues

- Sphere + `decompose()` / `batched_locate()`: CGAL's sweep calls `Compare_x_2`, whose precondition is `p.is_no_boundary()`. A spherical arrangement with a vertex on a pole or on the identification curve therefore raises CGAL::Precondition_exception (verified: a triangle with a vertex at the north pole fails, one inside a single octant works). Documented in the header; not blocked in code because it works for boundary-free arrangements. The Python layer may want to catch it.
- Linear kind + `he_directed_curve()` / `face_polygon()`: for the halfedge whose direction is opposite to the stored ray, `KindOps::construct_opposite` must reverse a ray, which `Arr_linear_object_2` cannot represent through any public constructor -> Error(Unsupported) propagates (2 of the 3 unbounded faces in the test). The linear KindOps author should confirm this is the intended contract (kind_ops_base.hpp already says "rays: Unsupported").
- `Arr_trapezoid_ric_point_location<sphere Arr>` compiles but aborts at construction (Td_traits precondition) -> KindPolicy<SphereTypes>::supports_trapezoid = false. If a future CGAL fixes this, only the specialisation needs flipping.
- `Arr_triangulation_point_location` compiles for Linear but calls point() on vertices at infinity -> runtime assertion; disabled in KindPolicy. It also would be geometrically wrong for any curved kind (it inserts straight constraints), which is why it is enabled for Segment only.
- `insert_curve()` with an XCurve box on a kind where Curve_2 != X_monotone_curve_2 routes through `KindOps::to_curve()`; that path is implemented but untested (my stub ops does not implement to_curve). Worth a test once the real KindOps exist.
- clone()/assign() preserve vertex/halfedge/face ids (they live in the copied ElementData) but NOT curve ids: CGAL allocates fresh Curve_halfedges nodes, so the clone's curve handles get new ids. Positional order in curves() is preserved.
- ASAN validation was attempted but the instrumented binary was still running after ~25 minutes; a macOS MallocScribble/MallocGuardEdges run was used instead (clean). A CI ASAN run on a smaller input would still be worthwhile.
